# Running and testing the agent layer

Written for engineers working on this repository.

All commands run from `backend/control` unless noted. The first `make` target
creates `.venv` and installs `.[dev]`, which carries pytest, aiosqlite and
trio; the production image ships none of them.

## The suites

```bash
make unit           # pure logic, no I/O
make contract       # the schemas and the provider contracts
make integration    # through the product, SQLite
make test           # everything, plus the scripted eval packs
```

Integration and e2e on **SQLite** is what the Makefile does. CI runs them
against **PostgreSQL 16**, which enforces foreign keys SQLite does not, so a
test that seeds a row referencing a run that does not exist passes locally and
fails in CI. To reproduce CI:

```bash
docker run -d --rm --name pg -e POSTGRES_PASSWORD=toxagent \
  -e POSTGRES_USER=toxagent -e POSTGRES_DB=toxagent -p 5432:5432 postgres:16
pip install -e '.[dev,postgres]'
export TOXAGENT_DATABASE_URL=postgresql+asyncpg://toxagent:toxagent@localhost:5432/toxagent
export TOXAGENT_ALEMBIC_URL=postgresql+psycopg://toxagent:toxagent@localhost:5432/toxagent
export TOXAGENT_TEST_DATABASE_URL="$TOXAGENT_DATABASE_URL"
export TOXAGENT_REQUIRE_POSTGRES=1
alembic -c alembic.ini upgrade head     # forward-only, from empty: the production contract
python -m pytest -q tests/integration tests/e2e
```

`TOXAGENT_REQUIRE_POSTGRES=1` turns a skip into a failure, so losing the URL is
loud rather than silent.

Two generated files are checked by unit tests and must be regenerated when the
product's shape changes — an intent, flag, profile, tool, queue, provider,
schema version:

```bash
python -m evals.architecture_inventory --write
python -m evals.capability_matrix --write
```

The API document the frontend types against is checked the same way:
`python scripts/export_openapi.py --check`, and regenerated by dropping
`--check`. The frontend then needs `npm run openapi:types`.

## Driving a turn without a model

`tests/e2e/test_scripted_runtime.py` installs a scripted runtime: you write an
async function that receives the turn and calls tools in order. This is how
every end-to-end test of this layer is written, and it is the fastest way to
see a change work.

```python
async def script(turn) -> None:
    assert turn.tool_context.profile == "decision_support_read"
    read = await turn.call_tool("get_analysis_slice",
                               {"analysis_id": analysis_id, "section": "herg"})
    await turn.call_tool("submit_grounded_answer", {
        "answer_markdown": "The hERG label is {{label}}.",
        "claims": [{"local_ref": "label", "kind": "classification",
                    "text": "The model labels this compound a hERG blocker.",
                    "observation_id": read["observation_ids"][0],
                    "field_path": "predictions.herg.label"}],
        "limitations": [{"code": "screening_not_safety_assessment", "text": ""}],
    })
```

The turn also exposes `turn.system_prompt`, which is how a test asserts that a
flag actually changed what the model was told rather than only what the server
recorded.

Useful starting points:

| File | Shows |
|---|---|
| `tests/e2e/test_serving_routes_through_the_product.py` | Each route, its profile, and its contract |
| `tests/e2e/test_case_revision_through_the_product.py` | A margin, a corrected exposure, and what it marks |
| `tests/e2e/test_release_gate.py` | Review, repair and partial release |
| `tests/e2e/test_budget_phases_through_the_product.py` | Budget, phases and invalid calls |
| `tests/integration/test_investigator_contract_through_the_product.py` | The contract and case view reaching the prompt |

## Rollout flags

Every capability in this layer is behind a flag in
`src/toxagent/platform/flags.py`, each with an owner, an added-on date and the
condition under which it should be removed. **All of them default to off.** Set
one with `TOXAGENT_FLAG_<NAME>=1`.

The ones this layer is made of:

| Flag | Turns on |
|---|---|
| `answer_draft_v2` | The v2 answer schema: local claim refs, server-resolved values, typed stop |
| `scientific_case_v1` | The case, carried across turns per subject |
| `subject_binding_v1` | One bound subject per message, frozen in the run envelope |
| `investigator_contract_v1` | The goal contract, the four routes and the six-group case view |
| `scientific_procedures_v1` | `run_scientific_procedure` |
| `scientific_primitives_v1` | `compute_exposure_margin`, `get_chembl_activities` |
| `scientific_skills_v1` | The dynamic skill arm: an index in the prompt, bodies read on demand |
| `evidence_full_text_v1` | `read_evidence_text` over captured full text |
| `activity_replay_v1` | Activity screenings, replayed from the pinned frozen file |
| `claim_reviewer_v1` | The independent reviewer turn |
| `release_gate_v1` | A candidate answer, reviewed before release |
| `typed_stop_v1` | A draft may declare why it stopped |
| `fixed_workflow_v1` | Arm B of the study: a fixed pipeline, same tools and gates |

`scientific_primitives_v1` also builds a **live ChEMBL provider**. On a frozen
deployment set `TOXAGENT_CHEMBL_PROVIDER=none`, or the run can reach the
network; the effective product reports `providers.activity_lookup` so a
benchmark preflight can refuse an arm that has it.

A deployment answers for itself: `GET /v1/system/effective-product` returns
every flag, the budget, the release policy and the pinned providers. That is
what the benchmark compares arms on, and what to read first when a run behaves
unexpectedly.

## A live local deployment

```bash
export TOXAGENT_DATABASE_URL=sqlite+aiosqlite:///./local.db
alembic -c alembic.ini upgrade head
export TOXAGENT_STATIC_TOKENS="dev:dev-user:expert"
export TOXAGENT_RUNTIME_KIND=opencode TOXAGENT_OPENCODE_URL=http://127.0.0.1:4096
export TOXAGENT_PROVIDER_ID=... TOXAGENT_MODEL_ID=...
export TOXAGENT_FLAG_ANSWER_DRAFT_V2=1 TOXAGENT_FLAG_SCIENTIFIC_CASE_V1=1 \
       TOXAGENT_FLAG_INVESTIGATOR_CONTRACT_V1=1
python -m uvicorn toxagent.api.app:create_app --factory --port 8001
```

`TOXAGENT_RUNTIME_KIND` has no default that names a runtime: a deployment says
which one it has, or starts with none. `GET /health/ready` reports the mode it
came up in.

For the whole stack in containers, with the frontend and the predictor, use
`./bin/toxagent` from the repository root — see the [root
README](../../README.md).

## Reading a finished run

| Endpoint | Shows |
|---|---|
| `GET /v1/sessions/{s}/runs/{r}` | Status, failure code, configuration snapshot, tool calls with phases, phase usage |
| `GET /v1/sessions/{s}/runs/{r}/result` | Disposition, review status, execution and knowledge outcomes |
| `GET /v1/sessions/{s}/runs/{r}/decision-state` | The goal contract the turn read, propositions, coverage, stop reason, review verdicts |
| `GET /v1/sessions/{s}/runs/{r}/answer-drafts` | Every draft, including the rejected ones with their violations |
| `GET /v1/sessions/{s}/runs/{r}/dossier` | The case as of this run |
| `GET /v1/sessions/{s}/cases/{c}/events` | The case's operation log |
| `GET /v1/sessions/{s}/events:list?run_id=` | The run's event stream, including schema errors on refused calls |

When a turn did something unexpected, the order that usually finds it: the
decision state (what was it asked, and what did it say it stopped on), then the
drafts (what did the validator refuse), then the tool calls (what did it
actually read).
